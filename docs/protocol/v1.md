# Faravan wire protocol v1

Status: protocol v1.0, frozen. This document specifies the current v1 runtime's
wire contracts. The v0 coordinator, daemon, Docker backend and Firecracker
research runner have been retired. Only the read-only historical verifier
remains, as described in section 11. Implementations MUST demonstrate the
contracts below before advertising v1 support. The key words MUST, MUST NOT,
SHOULD, SHOULD NOT and MAY are normative as in RFC 2119.

## 1. Scope and non-goals

A borrower publishes an immutable signed Job. A lender's outbound-only daemon
claims an Attempt, enforces local policy in an isolated execution environment,
and publishes a signed Result containing a self-reported Receipt and artifact
references. The coordinator is a queue and content-addressed blob store.
A group is a **circle**, not a v0 collective.

The native objects are Job, Attempt, Result, Receipt and Cancellation. CLI, CI,
MCP Tasks, A2A 1.0 and harness sessions are adapters: their task/session IDs MUST
NOT confer lease authority or replace the native attempt ID and generation.
A mapping MUST retain native IDs durably and propagate cancellation into the
native API. MCP/A2A cancellation is not evidence that a guest process stopped.
Adapters MUST pin the external protocol revision they implement rather than
assuming similarly named task APIs have stable semantics.

Not specified: payments, credits, marketplaces, trusted execution attestation,
result-quality verdicts, provider billing/account selection, sandbox implementation,
provider-policy eligibility, automatic merge/push, or exactly-once execution.
Input encryption against the coordinator is deferred to v1.x. Source and
transcripts are plaintext to authorized circle members and the coordinator in
v1.0; the assigned lender can retain them.

## 2. Principals and trust model

| Principal | Authority and limits |
|---|---|
| Circle owner/root | Holds an offline-capable Ed25519 root key; signs invites and membership rosters. Root compromise compromises circle membership. Root is not a model/provider credential. |
| Device | Holds its own Ed25519 key. A current member can read circle data, publish its own jobs, offer capacity and upload bounded artifacts. An author can cancel its own nonterminal jobs. |
| Lender | Chooses whether to claim, may decline for local policy, and controls its own machine. A signature identifies its claims; it cannot prove those claims truthful. |
| Borrower | Chooses the circle/source, verifies results against the expected job and retained attempt, reviews/tests candidate code before use. |
| Honest coordinator | Authenticates requests; atomically serializes state transitions, quotas and idempotency; checks current root-signed membership; stores bytes and acknowledgements durably. |
| Malicious coordinator | Can read plaintext, censor, delay, replay still-valid rosters, withhold artifacts, lie about attempts/status, fork views, and offer duplicate execution. It cannot mint root/device signatures or alter bytes under an independently trusted digest without detection. |
| Network attacker | Must be excluded by correctly validated HTTPS. Signatures also bind request targets and bodies; they do not hide metadata or replace TLS. |
| Hostile job/result | Can contain malicious code or archives. Signatures, membership and content addressing are not a safety or correctness verdict. |

The single-accepted-result guarantee assumes one honest, durable, logically
serial coordinator for the circle. Device signatures provide independent identity
and content integrity, **not coordinator-independent scheduling consensus**.
Clients MUST NOT claim global freshness, uniqueness or receipt truth merely
because a signature verifies. A malicious coordinator can equivocate about
leases; preventing that requires a separate transparency/consensus design.

All members can read all jobs/artifacts in their circle. Private subgroups need
different circles; v1.0 has no per-job ACL. Credentials, provider account
identifiers, private keys, tokens and host paths MUST NOT appear in public
receipts, capability advertisements or signed jobs.

## 3. Encoding, IDs and signatures

### 3.1 Wire encoding

Control bodies are UTF-8 JSON, media type `application/json`, maximum 262144
bytes and nesting depth 16. Senders MUST serialize JSON control bodies and
signed envelopes using RFC 8785 JCS without a BOM or trailing newline.
Receivers MUST reject duplicate members, invalid UTF-8, unpaired Unicode
surrogates, fractions, negative zero, nonfinite/unsafe numbers, unknown properties
and noncanonical wire bytes. The protocol numeric profile allows ONLY safe
integers (absolute value <= Number.MAX_SAFE_INTEGER), with per-field bounds.
Durations use whole seconds/milliseconds, sizes bytes, and times RFC3339 strings.
The general canonicalize() primitive implements full RFC8785 finite binary64;
its numerical edge vectors do not imply those numbers are valid protocol bodies. Pretty-printed documentation/examples are parsed then canonicalized
before transmission. Object keys are case-sensitive.

Integers are nonnegative IEEE-754 safe integers unless a narrower bound is
specified. Timestamps are real UTC calendar times exactly
`YYYY-MM-DDTHH:mm:ssZ`; leap-second `:60` is not accepted. JSON Schema format
assertion MUST be enabled; schemas alone do not check cross-field invariants.

A content digest is `sha256:` followed by 64 lowercase hex characters. A path
digest is those 64 hex characters without the prefix. Artifact digests hash
raw bytes. Job/result/cancellation digests hash JCS **payload** bytes, not the
signature wrapper. Circle, intent, attempt and invite IDs are canonical
lowercase UUIDs. An intentional rerun MUST use a new `intent_id`; a transport
retry MUST retain the original signed job and intent.

### 3.2 Signed envelopes

Job, Result, Roster, Invite, Cancellation and Leave use:
`{"payload":{...},"signature":{"algorithm":"Ed25519","key_id":"sha256:...","value":"..."}}`.
Receipt is embedded inside Result and covered by that signature; it is not
separately signed.

For kind `job`, `result`, `roster`, `invite`, `cancellation`, `request` or `leave`,
signature input is UTF-8 `faravan/<kind>/v1`, one NUL byte, then the raw
32-byte SHA-256 digest of JCS(payload). There is no hex text in that final
32-byte portion. The signature is Ed25519, 64 raw bytes encoded as unpadded
base64url (86 characters). Public keys are raw Ed25519 32-byte keys encoded
as unpadded base64url (43 characters). Decoders MUST reject noncanonical
base64url including nonzero unused bits. A key ID/fingerprint is SHA-256 of
the raw public key, using the digest string form. Implementations MUST
validate key/signature lengths and Ed25519 validity, not just a schema regex.

Roster and Invite use the root signature. All other signed objects use the
device key.

One more domain is not an envelope: `faravan/invite-binding/v1`. An **invite
binding** is a bare signature object `{"algorithm":"Ed25519","key_id":"sha256:...","value":"..."}`
(invite-binding.schema.json) made with the one-time **invite private key**
over UTF-8 `faravan/invite-binding/v1`, one NUL byte, then the raw 32-byte
SHA-256 of JCS(the complete Invite envelope, signature included). `key_id` is
the fingerprint of the Invite's `invite_public_key`. It is verified only
against an invite public key the verifier derived itself (section 5.1). Every verifier MUST check the expected kind/domain, schema,
signature, root-pinned roster, identity equalities, circle and independent
expected job/attempt binding before displaying a result as verified,
downloading its artifacts or extracting its candidate. Server-returned
metadata MUST NOT supply the only expected job identity.

### 3.3 Request proof (including reads)

Every request carries `Faravan-Proof`: unpadded base64url of a JCS signed
request envelope. Its payload fields are:

| Field | Required meaning |
|---|---|
| schema | Literal `faravan.request.v1`. |
| circle, key_id, roster_epoch | Circle UUID, authenticated device fingerprint and exact current accepted roster epoch. Bootstrap uses epoch 0. |
| method | Exact uppercase GET, HEAD, POST or PUT. |
| target | Exact externally visible absolute URL, including path and raw query, excluding fragment. |
| body_digest, content_length | SHA-256 and byte count of the actual body; empty-body GET/HEAD hashes zero bytes and has length 0. |
| content_type | Exact Content-Type header value; empty string for a bodyless GET/HEAD. |
| artifact_media_type | Exact Faravan-Media-Type for artifact PUT; empty string elsewhere. |
| idempotency_key | Exact Idempotency-Key for POST; empty string for GET/HEAD/PUT. |
| created | Integer Unix seconds. |
| nonce | At least 128 random bits in canonical unpadded base64url, 22–86 characters. |
| lan_mode | Optional literal `true`; required for a provisioned LAN-mode circle and absent in strict mode. Must match the signed roster/invite transport mode, not merely the target URL. |

Clients also send `Faravan-Version`, a dotted release version or `unknown`.
This unsigned header is a compatibility hint. It grants no authority. When a
host configures `min_member`, it checks authenticated member writes before
mutation or response replay. A missing, unreadable or older version receives
409 `client_update_required`, with `min_member`, `client_version`, a fixed
update instruction, `retryable:false` and `outcome:not_applied`. Reads and
bootstrap enrollment/roster recovery remain available. A host with no minimum
accepts legacy clients. App, CLI and MCP requests use the device's installed
release; a source checkout without VERSION reports `unknown`.

The signature key ID MUST equal payload.key_id. Server and client MUST agree
on a configured public origin; proxies MUST NOT reconstruct the target from
untrusted forwarded headers. Redirects MUST NOT forward proof or enrollment
secret; the client must verify the new origin separately and re-sign.
Query order/escaping is signed as sent. Servers MUST reject ambiguous path
normalization, dot segments, duplicate query parameters and encoded slashes
rather than reinterpret them after verification.

This deliberately small signed request envelope reuses the same JCS/Ed25519
verifier as the portable objects, avoids a second HTTP signature canonicalization
profile, and binds all routing, body and idempotency inputs. Its cost is a
nonstandard header and an explicit public-origin agreement. RFC 9421 could be a
future negotiated transport profile; a v1.0 peer MUST NOT silently substitute it.

Proof age MUST be at most 300 seconds, future skew at most 60 seconds. The
coordinator MUST atomically reject a previously seen (key_id, nonce), retaining
nonces through the inclusive request-proof validity window (created + 300
seconds); deletion is safe only at created + 301 seconds, at most 361 seconds
after receipt with the allowed future skew. Each retry uses a fresh proof
and nonce but the original idempotency key/body. Replaying a proof is not an
idempotent retry. Membership, epoch and signature are checked before
operational content is returned or a write commits. Uploads verify the proof
before streaming, then compare actual length/hash before committing.
Body buffering is forbidden for artifact uploads.

Every operational write, including roster publication and artifact upload,
requires proof of possession of a **current device key**. Reads also require
current circle membership; knowledge of a digest grants no access.
The narrowly scoped enrollment bootstrap below is the only exception: it
creates a pending request, not operational membership or job authority.

## 4. Objects and field tables

Machine-readable definitions are the five adjacent JSON Schema 2020-12 files.
Their example-domain $id values are stable schema identifiers, not live
download services; resolvers MUST load the adjacent files locally/offline.
OpenAPI defines the remaining control objects.

### Job (job.schema.json)

| Payload field | Contract |
|---|---|
| schema, circle | `faravan.job.v1`; configured circle UUID. |
| author, roster_epoch | Author device fingerprint and epoch when signed. Key MUST be current at publish/claim; publication uses the current epoch. |
| intent_id | UUID chosen and persisted by author for this submit intent. |
| created_at, expires_at | Creation and hard execution-authority deadline; expiry MUST follow creation. |
| max_attempts | 1–3 execution starts. A claim or pre-start release/failure/timeout does not consume this budget. |
| source | Exactly one of: pinned HTTPS Git, content-addressed archive, or `{kind:"none"}` (an empty workspace). Required; never implied (below). |
| prompt | ArtifactRef with text/plain. |
| requirements | Mandatory capabilities, egress and all limits; optional harness list and model constraint. |
| result | Optional `{kind}`, `message` or `files`; requires the `results_v1` capability. See Typed results below. |
| verify | Optional `{cmd}`, fixed before signing. Requires the `verify_v1` capability and a `wall_seconds` above 180. See Checks below. |
| parent | Optional `{job_digest,result_digest}` linking the exact result used by a follow-up; requires `parent_link_v1` on host and lender. |
| input_protection | Literal `none` in v1.0. |

Publish MUST reject expired jobs, creation more than 60 seconds in the future,
a missing referenced input blob, or wrong-circle/author signatures.
A job's recorded roster_epoch may be older than the current epoch after
publication; claim verifies that its author is **still current** and that
the archived signing epoch actually authorized it. An epoch change alone
does not invalidate immutable jobs.

Git source fields: `kind:"git"`, HTTPS `url`, `object_format:"sha1"|"sha256"`,
and full lowercase `commit` (40 or 64 hex characters respectively). Branches,
tags and abbreviated revisions are forbidden. Consumers MUST fetch that
exact object and verify checkout identity, including explicit treatment of
submodules/LFS: v1.0 MUST NOT fetch them implicitly. Git URLs MUST have no user
info, fragment or embedded credential, and staging must apply SSRF/egress
restrictions. Private source credential provisioning is local and out of band.
Archive source fields: `kind:"archive"` and `artifact` of application/gzip.
Its digest identifies compressed bytes, not a canonical filesystem tree.
No-source fields: exactly `{kind:"none"}`. The agent starts in an empty folder
(writing, analysis, questions, new scripts, images or data). It requires `result`.

### Typed results (results_v1)

What a job returns has three kinds (`RESULT_KINDS`, read with `resultKind()` in
lib/protocol):

| Kind | Encoding in the job | What comes back |
|---|---|---|
| branch | `result` absent (the only encoding, so every legacy job is unchanged) | Code changes: a diff, else a tree. |
| message | `result:{kind:"message"}` | The agent's final message (Markdown, in the signed transcript) plus any files it saved in `faravan-output/`. Older agents may still use `faravan-output/`. |
| files | `result:{kind:"files"}` | The files the agent saved in `faravan-output/` or the legacy `faravan-output/`. |

A job has `result` exactly when `requirements.capabilities` contains
`results_v1`, and a `{kind:"none"}` source requires `result`. A validator that
does not know `results_v1` refuses such a job with `unsupported_version` before
schema checks, so older hosts, lenders and clients never run or mis-read it. The
host offers it only to lenders that advertise `results_v1`. For `message` and
`files` the candidate is a gzip tar of `faravan-output/` and, for compatibility,
`faravan-output/` (entry names start with one of those roots), never a diff and
never the source tree.

### Linked follow-ups (parent_link_v1)

A follow-up is a new signed job. Its optional `parent` names the earlier job
and the exact result used to prepare its source. `parent` is present exactly
when `requirements.capabilities` includes `parent_link_v1`. The sender checks
host support before fetching the parent or uploading new artifacts; the host
claims the job only for a lender that advertises this capability. Job lists
omit parent-linked jobs for clients whose `Faravan-Client-Capabilities` header
does not include `parent_link_v1`, before pagination.

The link is the requester's signed assertion. It grants no access to the
parent and does not reuse its approval or permissions. The lender must accept
the new job. A lender can open the parent in the same circle if it remains
available to that device. Older jobs keep their local thread metadata, with no
new claim about a portable parent link.

### ArtifactRef (shared job schema definition)

| Field | Contract |
|---|---|
| digest | SHA-256 of exact bytes, prefixed form. |
| bytes | Exact nonnegative length, at most 1073741824; deployment may advertise less. |
| media_type | application/gzip, text/x-diff, text/plain or application/x-ndjson. |

Candidate MUST be text/x-diff or application/gzip. Transcript MUST be
application/x-ndjson or text/plain. A gzip archive MUST contain the restricted
tar format in section 9. MIME type never authorizes inline execution.

### Attempt (coordinator record; not a portable signed assertion)

| Field | Contract |
|---|---|
| attempt_id, job_digest | Fresh UUID and independently verified job payload digest. |
| generation | Strictly increasing safe integer for each new claim of that job, starting at 1; never reused. |
| holder | Authenticated claiming device fingerprint. |
| state | active, completed, released, failed, expired or cancelled. |
| claimed_at, lease_expires_at | Coordinator times; expiry is exclusive. |
| execution_started_at | Null until the holder's authenticated start transition commits; then immutable coordinator time. This is a lender declaration, not proof that a process ran. |
| execution_observed_at | Null until the backend reports that its entrypoint launched; then immutable coordinator time. This is execution evidence, separate from the replay fence in `execution_started_at`. |
| reason | Null while active/completed; bounded explanation for other terminal states. |
| compute_stopped, stopped_at | Initially false/null; holder-reported cessation and its timestamp. Never implied by lease expiry. |

Attempt IDs are not bearer tokens. The tuple (circle, job_digest, attempt_id,
generation, holder), current membership and unexpired lease confer authority
only when checked transactionally by an honest coordinator. Attempts remain
addressable for crash reconciliation. No guest-internal phase is a wire state.

### Result (result.schema.json)

| Payload field | Contract |
|---|---|
| schema, circle | `faravan.result.v1`; exact job circle. |
| job_digest, attempt_id, generation | Exact job and active attempt being completed. |
| executor, roster_epoch | Current holder fingerprint and signing roster epoch. |
| submitted_at | UTC claimed submission time; not trusted execution evidence. |
| candidate, transcript | ArtifactRefs, already stored and available within the same circle. |
| receipt | Effective execution configuration and timings. |
| checks | Optional (`verify_v1`). At most one entry for the job's `verify.cmd`. See Checks below. |
| output | Present exactly when the job has `result`: `{kind}` equal to `job.result.kind`. Requires an `application/gzip` candidate, `receipt.candidate_format: tree` and no diffstat, base_tree or diff_unavailable. |

Coordinator AND consumers MUST enforce:
job.author == job.signature.key_id;
result.executor == result.signature.key_id == attempt.holder;
job.circle == result.circle == configured circle;
result.job_digest == independently expected job digest;
result.attempt_id/generation == the accepted/current attempt being checked;
and resultKind(result.output) == resultKind(job) (both absent for branch).
For historical accepted results, use the preserved acceptance attempt, not
an invented fresh lease. Request signer MUST also equal author on publish
and result.executor on completion. Result acceptance means recorded output,
not correct code, verified model use, payment or an evaluation verdict.

### Budget observations (budget_v1)

A borrower MAY sign `payload.budget_v1` with `max_list_usd` (whole US dollars,
1–100000) and/or `effort` (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`,
`max`). Whole dollars preserve v1's integer-only numeric profile. The job MUST
also require the `budget_v1` capability. Clients MUST refuse a host without
`budget_v1` before publishing it. A claiming lender MUST advertise the capability
and have a current heartbeat listing it.

Only such a job receives `receipt.budget_v1`. It contains token classes, list
cost in integer `list_usd_micros` (or null when unpriced), catalog revision,
served model and effort, and `stop_reason` (`done`, `budget`, `time`, `owner`,
`provider_limit`, `error`). Reasoning tokens are included in output, not added
to it. Window utilization, account identifiers, calibration and reservations
MUST remain on the lender's computer.

A stopped run can return its one result with the work so far. For a legacy job,
the transcript begins with the stop reason and an explicit partial-work label;
the lender MUST NOT add extension fields to that receipt. A stop request alone
is neither proof of cessation nor proof that work was delivered.

### Automatic model and effort (auto_run_v1)

A borrower who does not name a model or an effort MAY sign `payload.auto_run_v1`
with one field, `intent`: `cheapest` or `strongest`. The job MUST also require the
`auto_run_v1` capability, and MUST NOT carry `requirements.model` or
`budget_v1.effort`. A validator that does not know the capability refuses the job
with `unsupported_version`, so an older lender never runs it as an explicit request.
`budget_v1.max_list_usd` still applies.

The claiming lender makes the choice once, from the exact model and effort pairs it
offers (`model_effort_pairs_v1`) at or below its live effort cap. `cheapest` is the
lowest list price in its pinned price catalog, then the lowest effort, then the model
id. `strongest` is the highest rank in a small versioned table, then the highest
effort at or below the cap. The claim advertisement names exactly that one pair. The
lender keeps the pair with the claim and uses it for the allowance check, the
reservation, the agent command and any replay; it never chooses again for the same
claim. If the live cap falls below the pair before launch, the lender declines.

A result for such a job carries `receipt.auto_run_v1` (`intent`, `model`, `effort`,
`rule_version`, `reason`, `capped`, `pricing_revision`) and lists `auto_run_v1` in
`capabilities_applied`. Both are the pair the lender passed to the agent. They are not
a provider report: the served model stays in `receipt.model` and the served effort is
not reported. A host or client MUST refuse a receipt whose intent differs from the job.

### Checks (verify_v1)

A job with `verify.cmd` asks the lender to run that command after the agent
ends. The current Docker backend collects the returned candidate, removes
the agent sandbox, then rebuilds the source in a fresh check sandbox. Diffs
are applied to the original source; tree candidates supply the returned tree.
For output-only results, the original source is rebuilt and the returned output
folder is added. Older lenders used the agent sandbox, so `verify_v1` alone
does not prove which isolation method was used.

The lender reserves 180 s of the job's budget for collecting and checking the
work. Check setup, stopping and removal consume part of that reserve. A failure
before the command starts can return the work with a skipped check. Cancellation
or unverified removal of the agent sandbox can still fail the job.

Each `result.payload.checks` entry (defined as
`receipt.schema.json#/$defs/check`) has `cmd`, `exit` (null when none was
observed), `timed_out`, `parser` and `summary` (counts only, never log text),
`changed_test_files` (observed test and config differences between the original
agent workspace and the rebuilt check workspace) and `observed_by`, always
`sandbox`. Optional `duration_ms` is measured command time. Optional `timeout_ms`
is the timeout actually enforced for the command. Unknown timing is omitted.
An optional `skipped` gives a fixed, safe reason when the command did not start;
executed commands omit it.

These are observations by the lender's software, kept apart from the agent's
claims. The fresh check keeps the job's image and network policy and may use the
lender's provider allowance. Returned tests, configuration and tools remain
agent controlled. A signed passing check is not independent proof of correctness.
A result without `checks` means no check was requested or the lender did not
support `verify_v1`; readers MUST show nothing for it.

Checks may also carry `duration_ms`, the measured duration of that command,
and `timeout_ms`, the time limit actually enforced for that command. Each is
an optional non-negative integer. Missing timing stays unknown: a reader must
not borrow the whole job's duration or requested wall limit. A timed-out check
can say “timed out after 5 min” only when its recorded `timeout_ms` is 300000.

### Receipt (receipt.schema.json)

| Field | Contract |
|---|---|
| schema, self_reported | `faravan.receipt.v1`, true. |
| harness, harness_version | Effective harness ID/version reported by lender. |
| model | Reported model ID or null when unobserved. |
| backend | Nonsecret isolation-backend ID; not host paths/credentials. |
| limits_applied | All five actually enforced ceilings, no greater than job ceilings. |
| egress_applied, capabilities_applied | Effective policy and required capabilities actually applied. |
| started_at, finished_at, duration_ms | UTC interval plus monotonic duration; finish >= start. |
| source | Exact verified source identity; MUST equal Job.source. |
| kit_hosts, kit_wider_hosts | Optional: the hosts the agent's own sandbox kit allows for its sandbox (as sbx reported them), and the inherited wildcards wider than those (for example `**.github.com`), which cannot be denied without blocking the kit and so stay open. Disclosure, not a restriction. |
| network_scope | Optional, Git jobs only: `clone_only` (GitHub reachable while the sandbox fetched the code, denied again before the agent started) or `whole_run` (the agent's own provider hosts include GitHub). Absent from an older lender, which keeps GitHub reachable for the whole run. |
| egress_evidence | Optional lender-device self-report: object mapping at most 32 targets to `allowed`, `denied` or `unknown`. |
| enforced_limits, unenforced | Optional lender-device self-reports: unique arrays, at most seven entries each, drawn from `cpu`, `memory`, `wall`, `output`, `storage`, `processes`, `network_bytes`. |
| usage | Optional lender-device self-report with all three keys `input_tokens`, `output_tokens`, `total_tokens`; each is a nonnegative safe integer or null when unknown. No other keys. |
| candidate_format, diffstat, base_tree, diff_unavailable | Optional. `candidate_format` is `diff` (candidate is `text/x-diff`) or `tree` (candidate is `application/gzip`). `diffstat` (`files`, `insertions`, `deletions`) is present only for `diff` and is computed from the signed diff bytes. `base_tree` is the Git tree ID of the snapshot the lender committed as base for an archive source. `diff_unavailable` (`git_unavailable`, `git_failed`, `archive_has_git`) says why a `tree` fallback was returned. |

For constrained jobs, harness/model/capability/egress fields MUST satisfy
requirements; unknown model cannot satisfy an exact model constraint.
Remote model truth remains self-report even if the routing control was
enforced. Unknown harness version uses the literal `unknown`, never invented
precision. Monotonic duration need not exactly equal wall-clock subtraction;
clock adjustments MUST NOT widen the enforced wall limit.

### Diff candidates

A lender SHOULD return the candidate as a unified diff, so the borrower reviews
changes and not a copy of the workspace. Inside the sandbox, before the agent
runs, the lender fixes a base: for a Git source the verified `source.commit`;
for an archive source a commit it creates by initializing a repository in the
extracted files and committing all of them. After the agent finishes, it runs
`git add -A` and `git diff --binary --cached --no-renames <base>` (excluding the
lender's own `.wf-*` directories), uploads the output as `text/x-diff` and
signs `candidate_format: diff` with the `diffstat`. Hooks, fsmonitor and
external diff drivers are disabled on the command line. The diff counts
against `output_bytes` like any candidate. If git is missing or fails, the
lender returns the `application/gzip` tree and sets `candidate_format: tree`
and `diff_unavailable`.

A borrower applies a diff candidate only after verifying the signed result, in
a new branch and never over the working tree. It MUST: require the base (the
job's `source.commit`, or for an archive a commit in its own history whose tree
equals `base_tree`) to be contained in its repository; refuse a patch that names
a path inside `.git`, an absolute path, a `..` component, a submodule, or a
symbolic link pointing outside the repository; and dry-run the patch against
the base before writing anything. `faravan apply` (lib/v1/apply.mjs) does
this using a temporary index, so neither the current branch nor the working tree
changes.

The four optional evidence/usage fields are self-reported by the lender device,
not independent attestation. Their absence preserves existing receipts; unknown
usage MUST be null, never an invented zero. They do not relax required limits
or capability checks. Egress target names MUST NOT expose secrets or host paths.

| members[] | Current members only: unique key_id, raw public_key, joined_epoch <= epoch, optional device_name (1-64 characters, as in the enrollment proof; the owner copies the name the joining device signed). Key ID MUST equal hash(public_key). Empty list revokes all operational access. |
| profile | Optional (v1.0 addition) owner-signed circle settings: `name` (required in the object) and optional `purpose`, each 1-256 characters, no control, format or bidi characters, no edge spaces. Absent in legacy rosters; a device without this addition rejects a roster that carries it. |

HTTPS except literal loopback or the explicitly signed LAN mode in section 7. Optional signed `display_name` labels the circle; optional `lan_mode: true` selects LAN mode. Optional signed `approval: "each"` says the owner approves each device by hand (absent: the owner's device approves automatically); optional signed `owner_name` (1-64 characters) names the owner's device for the joiner's "Waiting for {owner}" text. |
| root_fingerprint/root_public_key | Trust anchor carried through a trusted invitation channel; fingerprint MUST equal key hash and signature key ID. |
| invite_id/invite_public_key | UUID and raw Ed25519 public key for one-time enrollment approval. Private seed is never in this public envelope. |
| created_at/expires_at | Maximum invite lifetime 86400 seconds, expiry after creation. |
| Leave schema/circle/key_id/issued_at | `faravan.leave.v1`, exact circle, the leaving device's key ID (equal to the signer), UTC time. Optional message, section 5.2. |
| Cancellation schema/circle/job_digest | `faravan.cancellation.v1`, exact circle and job. |
| author/roster_epoch/created_at/reason | Original job author, current signing epoch, UTC time and bounded reason; signed by author. |

## 5. Identity, roster and enrollment

The owner provisions circle ID, coordinator origin, root public key and an
initial root-signed roster out of band. The root private key MUST NOT be held
by the coordinator merely to serve rosters. Owner maintenance uses a separate
current device key to PUT a root-signed roster. That endpoint stores the signed
bytes; it cannot approve membership without the root signature. To avoid an
expired-roster recovery deadlock, PUT /roster authenticates its RequestProof
against the **proposed unexpired root-signed roster**, and the proof epoch
MUST equal that proposed epoch. The signing device MUST appear in it. The
coordinator verifies the pinned root and strictly increasing epoch before
using the proposed membership. This is still current-device proof at commit,
not root-key possession alone. A same-epoch identical retry authenticates
against that same roster. Installing an empty roster (which leaves no device
able to make a write) is an explicit out-of-band owner operation, not this API.

Clients MUST pin (circle, origin, root fingerprint) from a trusted invite
channel before any network enrollment. A self-signed key fetched from the
coordinator is not a trust anchor. Invite links MUST put secret material only in
the URL fragment and MUST NOT put it in query logs/referrers. Clients MUST
remove it from browser history and MUST NOT log it.

The queue server serves an unauthenticated, self-contained HTML landing page
only for exact `GET /join` and `GET /i/{code}` (no query, trailing slash or
other public page; the one public data route is `GET /v1/invites/{code}` in
section 5.1).
This page is not an enrollment endpoint and needs no Faravan-Proof.
Responses use `Content-Type: text/html; charset=utf-8`, `Cache-Control: no-store`,
`Referrer-Policy: no-referrer` and a Content-Security-Policy with
`default-src 'none'`, `connect-src 'none'`, `base-uri 'none'`,
`form-action 'none'` and `frame-ancestors 'none'`; only inline page script
and styles are allowed. No external requests, assets, links or analytics run.
The page clears the fragment from browser history and decodes the bundle
locally. A signed `display_name`, when present, is rendered as plain text
and explicitly labeled unverified until the app checks it. The page does not
verify signatures or enroll the device. It keeps the original link in memory
for the explicit “Copy invitation” action, with a manual-copy fallback.
“Get Faravan” reveals local install steps; no installer is claimed. “I already
have Faravan” is a `faravan://join?link=<URL-encoded full invite link>` link that
hands the invitation to the installed app (`faravan open-link`, which opens the
join review and never joins by itself), and it also reveals the paste steps
because a browser gives no signal when nothing handles the scheme. The previous
`faravan://` scheme remains accepted. Missing or
malformed links say “Ask the person who invited you for a new link”. The page
at `/i/{code}` behaves as section 5.1 describes; `/join` keeps `connect-src 'none'`.

1. The owner's device registers the root-signed public Invite containing only
   invite_public_key. Its fresh 32-byte Ed25519 seed is carried only in
   coordinator origin + `/join#invite=` + unpadded base64url of
   JCS({invite: <root-signed envelope>, invite_private_seed: <base64url seed>}).
   The link must arrive through a trusted channel; self-signature is no trust pin.
2. The joining device generates its device key locally. EnrollmentRequest has
   invite, device_public_key and enrollment_proof. The proof is
   {payload:{circle,invite_id,device_public_key,device_name?},signature:{algorithm,key_id,value}}
   with signature format as in section 3.2. It signs UTF-8
   `faravan/enrollment/v1`, one NUL, then raw SHA256(JCS(payload)), using the
   invite private key. device_name is optional: a display name of 1-64 characters
   chosen on the joining device, without control, format or bidi characters and
   without leading or trailing space. When present it is part of the signed
   payload, so the coordinator cannot add, change or remove it. Owners show it
   with the device key fingerprint, but it is a claim, not an identity proof.
   key_id is the invite-key fingerprint. The independent
   device-key Faravan-Proof uses epoch 0 and proves possession of the new key.
   Enrollment requests MUST NOT transmit the private invite seed to the server.
3. The owner verifies enrollment_proof against its independently registered
   invite public key and exact circle/invite/device context, not a key supplied
   by an enrollment request. Each invite_id can approve at most max_uses
   distinct device keys (one when absent). Consumption is durable at both the
   coordinator and owner, and is not refunded by rejection, expiry or removal.
   Exact retries recover the same enrollment without consuming another use.
   Legacy invites retain enrollment_conflict for substitution; explicit
   max_uses exhaustion returns 409 invite_used. The joining client says:
   “This invitation was already used. Ask {owner} for a new one.”
   The owner name comes from the verified signed invite. The owner's online device then signs/publishes the
   next roster automatically, unless approve-each-device mode requires a click.
   If the owner is offline, the enrollment stays pending. Enrollment by itself
   is not membership. A coordinator cannot forge the invite signature.
4. A current device publishes the next root-signed roster. The server requires
   epoch > installed epoch, unchanged circle/root, valid timestamps and unique
   correctly hashed keys. Same epoch and identical bytes is a no-op; same epoch
   different bytes or a lower epoch is roster_stale. Epoch gaps are allowed.
5. GET own enrollment with new-key proof returns pending/approved/rejected/expired.
   Only approved returns a signed roster, which the joining client verifies
   against its pin and confirms contains its own key. Pending authentication
   MUST NOT read any other circle resource or another enrollment.

Bootstrap status remains retrievable with the same device proof for 24 hours
after enrollment request creation; then it is 410 enrollment_expired. Pending
enrollment expires at that deadline. Invite expiration controls request
creation, not subsequent owner approval within the pending window.
Operational devices subsequently use normal proof with the current epoch.
A pending new device may retry GET even when not yet a member; its epoch remains 0.

Each client/coordinator MUST durably remember the highest accepted roster
epoch for each pinned root/circle. Reject lower epochs and conflicting bytes
at the same epoch. Removing a member MUST remove current authorization, not
merge it into a stale active-key cache. Preserve authenticated old rosters and
keys separately for historical verification. Claimed timestamps alone do not
prove that an old signature predates revocation.

Roster validity bounds replay of a still-signed roster: issued_at cannot be
more than 60 seconds in the future; valid_until MUST be later than issued_at
and no more than 2592000 seconds (30 days) after it. Creation defaults to
604800 seconds (7 days). The owner refreshes online after half the validity
interval has elapsed. Expired rosters MUST NOT authorize
new operational requests or continued execution. GET /roster may use a proof
naming an older/expired epoch only to refresh, and still requires the key to
be a member of the server's current unexpired roster. PUT /roster uses the
proposed-roster rule above; neither exception authorizes job work under an
expired roster. Historical verification
does not require a currently unexpired roster. Clients SHOULD refresh before
renewal and before expiry; an offline/uncertain lender MUST stop before its
last verified authorization deadline. A malicious server can withhold a
newer roster until the old validity expires; anti-rollback alone cannot
eliminate this bounded stale-view window.

On roster replacement an honest coordinator MUST atomically fence active
attempts held by removed devices and cancel nonterminal jobs authored by
removed devices. A revoked holder's job may requeue if its author remains
current, unexpired and within budget. The removal makes old results
historically verifiable, not eligible for new acceptance. Root rotation,
lost-root recovery and reinstating a revoked key are outside v1.0; use a
new device key and an owner-signed new epoch for re-enrollment.

### 5.1 Short invites

A long link is about 1,100 characters because the Invite envelope rides in the
fragment. A **short link** carries only a code and the seed:

    <origin>/i/<code>#<seed>

`<code>` is 10 lowercase base32 characters (`[a-z2-7]{10}`), 50 bits drawn from
a cryptographic random source by the owner device; `<seed>` is the unpadded
base64url invite private seed (43 characters). A short link is about 80
characters. Browsers omit the fragment from HTTP requests and referrers.
The trusted app and CLI keep the seed out of requests. JavaScript served by
the queue can read the fragment, so a dishonest queue can capture the seed
when its landing page is opened. See the trust boundary below.

Publication. The owner device creates the root-signed Invite exactly as for a
long link, signs the **invite binding** (section 3.2) with the invite private
key, and POSTs `{code, envelope, invite_binding}` to the existing `POST /invites`
(invite-publication.schema.json). The server verifies the Invite against its
pinned root and circle, verifies the binding against
`envelope.payload.invite_public_key`, bounds the publication to 8192 bytes, and
stores it with the invite, keyed by `invite_id` and durable across restart.
Publication is idempotent: an exact repeat returns the stored publication, a
different envelope, code or binding for the same `invite_id` is
`enrollment_conflict`, and a code held by another invite is `conflict`. (Ed25519
is deterministic, so an exact retry yields identical bytes.) A bare Invite body
(no `envelope` member) is still accepted; such an invite has no code and only a
long link. A server that rejects the publication form with `invalid_request` is
an older server; the owner device falls back to the long link and says so.

Resolution. `GET /v1/invites/{code}` is public and needs no Faravan-Proof. It
returns `{"envelope": <Invite>, "invite_binding": <binding>}` (200), `404
not_found` for an unknown code and `410 enrollment_expired` once the Invite has
expired. It is the first unauthenticated v1 data route: it has its own
per-code limit of 30 requests per 60 seconds (429 `rate_limited`,
at most 4096 tracked codes), a fixed 8192-byte publication bound, no query
string, and returns only public material. It is read-only and `Cache-Control:
no-store`. The code is a lookup key, not a secret: 50 bits plus the rate limit
make enumeration impractical, and knowing a code yields nothing a joiner can
use, because every use needs the seed.

Joiner rule. A joiner that holds `<origin>`, `<code>` and `<seed>` MUST, before
trusting any field of the fetched envelope (including `root_public_key`,
`root_fingerprint` and `coordinator`):

1. rebuild the Ed25519 key from `<seed>` and check that its public key equals
   `envelope.payload.invite_public_key`;
2. verify the invite binding against that locally rebuilt public key;
3. verify the Invite envelope (shape, root signature, `root_fingerprint`);
4. require `envelope.payload.coordinator` to equal `<origin>`.

Only then is the pair equivalent to the long link
`<origin>/join#invite=base64url(JCS({invite, invite_private_seed}))`, and the
rest of enrollment (root pinning, enrollment proof) is unchanged. A client MAY
therefore implement resolution as "turn a short link into a long link" in front
of an unchanged long-link join path.

Why the binding is required. Without it, the seed check only ties the envelope
to `invite_public_key`, a value the server also knows. A malicious server (or
anything between the joiner and it) could return its own Invite with a root key
of its choosing, copy `invite_public_key` from the real one, and sign it with
the root it controls: the joiner would pin the attacker's root as the circle's
trust anchor and join a circle the attacker controls. A long link opened
directly in a trusted app carries the owner's envelope without a lookup.
The binding prevents substitution when the seed remains secret from the server.
Only a holder of the seed can sign it, and the signature covers the whole
envelope including the root key, so a substituted envelope fails step 2
(`invalid_signature`) and a substituted binding fails step 1 or 2
(`key_mismatch`, `invalid_signature`). Anyone who holds the link
(and so the seed) could build a binding; that is the same capability the link
already grants, since the seed alone enrolls a device.

Trust boundary. A queue that serves the landing page can replace its
JavaScript, capture the fragment seed and bind a replacement invitation to
its own root. Browser verification on that page cannot prevent this.
Protection against a dishonest queue requires an independently trusted
verifier, such as the installed app or CLI handling the original link
without first opening the queue-served page. This limit also applies to
long links opened on a queue-served page.

Landing page. `GET /i/{code}` serves the same page as `/join` with
`connect-src 'self'`. The page reads the seed from the fragment, fetches
`/v1/invites/{code}` from its own origin and checks steps 1-4 with WebCrypto
Ed25519 where the browser supports it. After success it shows “{owner_name}
invited you to {Circle}” (owner_name is a signed field). If the browser cannot
verify Ed25519 it shows “You're invited to a circle.” and says the app checks the
invitation; an unverified fetch never shows invitation names or the LAN notice.
If verification fails it shows an error and no name, and the open/copy actions
are disabled.

Deep link. `faravan://join?link=<URL-encoded short or long link>` is handled by
`faravan open-link <url>`; the previous `faravan://` scheme remains accepted.
It finds the running app through its private
discovery file (starting it if needed) and opens the browser at the app's join
review with the invitation filled in. It never joins; the person confirms in the
app. The app's session token stays in the local app URL and is never part of the
link, the landing page or either deep-link URL.

### 5.2 Leave requests (optional, added in v1.0)

A member can ask to be removed from the roster. The roster is root-signed, so only
the owner's device can publish the result; the request lets the member start that
without a human step, in the way enrollment approval does.

This is a **new, optional message**. It adds two routes and one signed object, and
changes no existing object, route, status code or signature. A device that does not
know it never sends it and never reads it. A coordinator that does not know it answers
`not_found`. A member whose coordinator or owner is too old still leaves locally, and the
owner removes the device by hand as before.

1. **Leave envelope.** Kind `leave`, signed in the usual envelope form
   (`faravan/leave/v1`, one NUL, then SHA256(JCS(payload))) by the leaving device's own key.
   Payload, all fields required and no others: `schema` = `faravan.leave.v1`, `circle`,
   `key_id` (the leaving device, equal to the signing key), `issued_at` (UTC, whole seconds).
   A device signs a leave only for itself. The signature is domain-separated, so no other
   signed object can be replayed as a leave and a leave cannot be replayed as one.
2. **POST /leave-requests** (any current member). Body `{"leave": <envelope>}`. The coordinator
   verifies the signature with the caller's roster key, `payload.key_id` equal to the caller,
   the right circle and `issued_at` not more than 60 seconds ahead and not older than
   30 days. It stores at most one open request per device (a repeat returns it) and answers
   `202` with `{leave_id, key_id, state: "pending", created_at}`. Storing it changes no
   membership, authority or job.
3. **GET /leave-requests** (any current member). Returns `{items: [...]}`, at most 100 open
   requests of devices that are still members, oldest first. Each item carries the leave
   envelope, so a reader never has to trust the coordinator's summary.
4. **The owner's device applies it.** Automatically, with no confirmation and also in
   approve-each-device mode, because it is the member's own choice. For each item it checks
   the envelope against that member's key **in its own current roster**, the exact circle,
   `payload.key_id` equal to the item's key, and the 60 second and 30 day bounds. It
   ignores anything else, and it never applies a request for its own device. It then publishes
   one root-signed roster, with epoch greater than the installed epoch, that omits every
   verified leaver. That is the ordinary roster replacement of section 5: the coordinator
   fences the removed device's attempts, cancels its nonterminal jobs and drops its leave
   request.
5. **What it does not do.** It does not retract data the member already shared and does
   not give the owner or coordinator any new power: a coordinator that forges, withholds or
   replays a request can at most delay a removal the member asked for, because a request
   no member signed fails the owner's check. Removing oneself a second time needs a new key
   and a new enrollment (section 5, reinstating a revoked key).

### 5.3 Member origin claims

A member that serves its own circle store at a public address can offer that address to the
circle's publishers. This is a **new, optional message**. It adds two routes and no signed
object, and changes no existing object, route or signature. A coordinator that does not know it
answers `not_found`.

1. **POST /member-origins** (any current member). Body `{"proposal": ...}`, an ordinary
   authenticated circle request. The proposal has no sender field: the sender is the roster
   member that the request proof names. Either `{schema: "faravan.member-origin.v1", state:
   "proposed", origin, generation, observed_at, valid_until}` (an exact `https` origin that the
   roster would accept, the route's generation, and when the evidence was observed and lapses,
   at most 7 days apart) or `{schema, state: "withdrawn", observed_at}`. It carries no local
   target, provider handle or credential. The coordinator keeps the newest claim per device and
   its request proof, and answers `202` with `{key_id, state, proposal_digest, created_at}`.
2. **GET /member-origins** (owner, steward or co-admin only). At most 100 current claims of
   current members. Each item carries the member's request proof, so a reader never has to trust
   the coordinator's summary.
3. **The publisher accepts it.** The publisher's device checks that the proof is a current
   member's own signature, for this circle's route and exactly the body bytes of the claim, and
   that the claim is neither withdrawn nor past `valid_until`. The decision is bound to the claim's
   digest and to the roster epoch it was reviewed against. Only then does the owner, steward or
   co-admin sign the origin onto that member's roster entry through the ordinary roster edit. An
   exact retry of an accepted claim changes nothing.
4. **What it does not do.** A claim is reach data. It never changes membership, authority or the
   roster until an authorized publisher signs it in, and a coordinator that forges or withholds one
   cannot publish an origin.

## 6. Lifecycle and concurrency

Every mutation MUST use a durable transaction or equivalent compare-and-swap
covering membership/epoch, job state, current attempt, generation, retry budget,
artifact availability and idempotency record. Atomic file rename alone is
insufficient. Reads MUST NOT write stale snapshots. Background expiry and
list projections MUST apply the same transactional rules as mutations.

Job states: queued -> claimed -> result-accepted, with terminal expired,
cancelled and failed. Attempt states: active -> completed/released/failed/
expired/cancelled. Terminal attempts retain their authority state; a late launch
observation and the monotonic false-to-true cessation report may still be recorded.

| Event/precondition | Job transition | Attempt transition/effect |
|---|---|---|
| Valid publish | absent -> queued | No attempt; attempts_started=0. |
| Claim eligible queued job | queued -> claimed | Allocate fresh ID, generation +1, execution_started_at=null, active; no execution budget consumed. |
| Start active holder before all deadlines | claimed -> claimed | Set execution_started_at once as a request fence; consume no execution budget. |
| Observe backend entrypoint launch | unchanged | Set execution_observed_at once after an authenticated start request and increment attempts_started once, even for a late observation. |
| Renew active holder before all deadlines | claimed -> claimed | Extend lease; same ID/generation. |
| Release active holder | claimed -> queued, or failed/expired | active -> released, record reason and revoke authority. |
| Fail active holder | claimed -> queued, or failed/expired | active -> failed, record terminal attempt reason. |
| Lease timeout | claimed -> queued, or failed/expired | active -> expired; old generation permanently fenced. |
| Last allowed attempt ends without result | claimed -> failed | Preserve terminal reason; no further claims. |
| Hard job deadline | queued/claimed -> expired | Active attempt -> expired; no further acceptance. |
| Valid completion | claimed -> result-accepted | active -> completed; persist result + original acknowledgement atomically. |
| Author cancellation | queued/claimed -> cancelled | Active attempt -> cancelled; revoke authority immediately. |
| Author revoked by roster | queued/claimed -> cancelled | Active attempt -> cancelled with reason author_revoked. |
| Holder revoked by roster | claimed -> queued/failed/expired | active -> cancelled with reason holder_revoked. |
| Stop report from current member holder | unchanged | Terminal record compute_stopped false -> true. |
| Exact completion retry already accepted | unchanged | Return original acknowledgement; do not rerun acceptance. |

Requeue after release/fail/timeout/holder revocation is permitted only if
job.expires_at > server now, author remains current, no backend launch was observed,
and attempts_started < job.max_attempts. For older attempts without an observation
field, the existing start marker remains the launch evidence. An
attempt that started the agent may have run in part, so however it ends (release,
fail, lease timeout, holder revocation) the job becomes `failed` with the reason on
its attempt, and is never offered again: running it again is the borrower's choice,
a new job with a new intent (T21). A coordinator built before this requeued such a job. Deadline takes precedence over exhausted
budget. A terminal job never returns to queued. Generation overflow fails
closed; no wrap/reset. A claim MUST NOT consume execution budget. The holder
MUST POST /attempts/{attempt_id}/start with {generation} after successful source
materialization and immediately before invoking its execution backend. The server
atomically checks current holder, ID, generation, membership, active state,
unexpired lease/job/roster and remaining budget; sets execution_started_at to
server time without incrementing attempts_started. A duplicate start with
a new idempotency key returns the same marker only while authority is still active.
An exact idempotent replay may return its historical acknowledgement; clients MUST
re-read the current attempt and recheck authority before invoking the backend.
Unknown or failed start outcomes MUST NOT authorize execution. Completion requires
a non-null start marker. Release, failure, lease timeout or revocation before start
costs zero until launch is observed; an observed launch retains the charge. Generation and attempt identity
MUST NEVER be rolled back, reset or reused to refund a pre-start decline.

After invoking the backend, the holder MUST POST
`/attempts/{attempt_id}/observed-start` only when the backend launch callback
confirms that the entrypoint was spawned. This records `execution_observed_at`
once and charges the execution budget once, even if the attempt has since ended. The holder MAY send `observed_at` as a
UTC whole-second timestamp; a retry preserves that time instead of the time the
coordinator receives it. Without that field the coordinator uses receipt time.
The request marker remains the replay fence; clients MUST use the observed
timestamp, not the request timestamp, to project Running or notify that work
started. A failed or delayed backend start leaves the observation null. The
guarded entrypoint shell waits for the coordinator to acknowledge its durably
recorded launch before it starts the agent; this observation is not proof that the agent did useful work.

The marker is an authenticated holder declaration of imminent execution, not
attestation. A crash between the committed marker and backend invocation does not
consume a budget slot. The server MUST NOT infer start from
renewal, release reason, compute_stopped, receipt timing or ambiguous old records.
Stores retain the old meaning for attempts without an observation field. Existing
counts are recalculated from the retained attempt records when the store upgrades;
unknown legacy markers MUST fail closed for start/completion.

Lease duration: minimum 30 seconds, default 120, maximum 300. Noninteger/
out-of-range requests are rejected, not silently rounded. On claim:
lease_expires_at = min(now + requested duration, job.expires_at,
current roster.valid_until). If less than 30 seconds remains, claim MUST fail
(job_expired or roster_expired as applicable); claim-next skips it.
Renew requires the current holder, matching generation, active state and
now < lease_expires_at. New expiry is
min(max(old expiry, now + duration), job.expires_at, roster.valid_until).
It never shortens or revives a lease; a refresh to a newer roster can permit
a later extension. Workers SHOULD renew with at least 30 seconds remaining
and MUST stop starting work/provider calls before their verified deadline.
They MUST use a conservative monotonic local timer, accounting for observed
network delay/skew; uncertain clock synchronization is reason to decline/stop.

Completion is accepted only if now is before job and lease expiry, author/
executor are current, the active attempt tuple matches, all referenced blobs
exist with exact length, requirements/receipt are consistent, and signatures
verify. Competing complete/cancel/expiry operations serialize: the first
eligible committed transition wins. A completion after committed cancellation
fails; cancellation after accepted completion is job_terminal. Neither
operation deletes historical output or undoes external side effects.

The coordinator MUST promise **at most one accepted Result per Job**, not
one execution. Failover, lease expiry and network uncertainty can produce
multiple executions or external effects. Clients MUST treat a transport
timeout as unknown outcome, reconcile durable state and retry idempotently.
Lenders MUST persist attempt/result publication intent locally before side
effects/transmission and inspect recorded attempts after restart before
continuing. Stale attempts MUST stop and MUST NOT publish as a new attempt.

## 7. HTTP endpoints, idempotency and errors

Base: `/v1/circles/{circle_id}`. HTTPS is required by default, except literal
loopback `http://127.0.0.1` or `http://[::1]`. Only circles created explicitly
in LAN mode MAY use HTTP on RFC 1918 IPv4, IPv4 link-local 169.254/16, IPv6
link-local fe80::/10, or a valid DNS name ending in .local. Public HTTP,
localhost names, ULA, wildcard/unspecified addresses and noncanonical origins
remain forbidden. Origins MUST exactly equal their normalized URL origin,
without credentials, path, query or fragment. TLS verification MUST NOT be disabled.

LAN permission is root-signed as `lan_mode: true` and exact `coordinator`
origin in the initial provisioning roster. The local provisioning record's
`lan_mode` MUST agree with that signed roster; neither a server environment
variable nor an untrusted request can grant LAN permission. Later rosters
preserve that origin/mode. Invites bind the same `lan_mode` and coordinator;
request proofs include `lan_mode: true` and MUST match provisioned transport
mode as well as the exact request target. Omission selects the strict default;
a false or otherwise unrecognized signed mode is rejected. All signatures,
nonce replay protection and freshness checks remain mandatory in LAN mode.

Before enrollment, members MUST see: “This circle uses your local network
without encryption; people on the same network could read uploaded code.”
Clients also return this warning with joined circle metadata. Signatures do
not provide confidentiality or authenticate unsigned coordinator responses.
No endpoint accepts proof, keys or secrets in URL query parameters.

Authentication classes: **M** current member RequestProof; **H** M plus
matching attempt holder; **A** M plus original job author; **E** restricted
new-device enrollment proof. Roster publication is M plus root-signed body.
All writes reevaluate current authorization at commit; reads reevaluate it
before returning bytes. Path circle and every signed circle MUST agree.
HTTP request-body schemas and responses are fully enumerated in openapi.yaml.

### Endpoint matrix

Unless shown otherwise, responses are 200 application/json. All POSTs require
Idempotency-Key. Every endpoint may return the shared errors below; the last
column lists operation-specific errors, not an exhaustive HTTP list.

| Method/path after base | Auth | Request -> success | Errors and idempotency |
|---|---|---|---|
| GET /capabilities | M | empty -> Capabilities | roster_stale/expired; safe read. |
| GET /roster | M | empty -> latest signed Roster | Proof may name a remembered older epoch for roster refresh, provided key is still current; safe read. |
| GET /rosters/{epoch} | M | empty -> root-signed Roster at exact positive integer epoch | Same current-membership rule and older proof-epoch allowance as /roster; not_found for an absent epoch. |
| PUT /roster | M + root | Roster -> stored Roster | roster_stale, invalid_signature; exact same epoch/bytes no-op. A newly listed key that asked to join is admitted only while one of its requests is pending, unexpired, for the same public key and from an unrevoked invitation, and only by a roster issued after every other request of that key was declined, revoked or expired; otherwise forbidden. **Retention (P17a).** A host deletes a job's request, code, result, receipt and progress 30 days after the job ends
(`terminal_retention_seconds`), together with every stored file no other job still uses (source archives, prompts, candidates,
transcripts); the quota they held is given back. Only a tombstone stays, so a retried completion, cancellation or resubmission of the
same envelope still gets its original answer. A host that restarts also removes blob files no row owns (a crash between a committed
deletion and the file removal). GET /jobs/{digest}/retention returns {job_digest, state, ended_at, retained_until, deletable} (`ended_at`
and `retained_until` are null while the job runs; `deletable` is true for a finished job and its author or the circle's owner device).
POST /jobs/{digest}/delete with `{}` deletes a finished job and its files at once (author or owner device; 409 conflict for a job that
has not ended; repeatable). The owner device is the member that last published a newer root-signed roster. Both routes need the host's
`retention_v1` capability; a member never sends them to a host without it.

Hosts advertising `stop_intent_v1` expose `GET` and `POST /attempts/{attempt_id}/stop-request`. Only the current holder of
the active, started generation can record a stop request. The coordinator stores its first request timestamp durably and
returns the same fact on retries. Any member that can read the job can read that fact. A stop request does not change the
Attempt state, revoke execution authority, or set `compute_stopped`; only the existing terminal transition and later
`POST /attempts/{attempt_id}/stopped` report do that. A new request after the attempt is terminal is rejected. Existing
clients keep their Attempt and JobView shapes; clients use this route only when the host advertises the capability.

Presence is an optional heartbeat (heartbeat.schema.json). A lending device posts it every 30 s from a timer
independent of claim-next, so a blocked, paused or resting device stays visible with its reason. The coordinator
takes the device from the request proof and the time from its own clock. A device is online when its last
heartbeat, or for an older lender its last claim-next poll, is under 90 s old; an older lender is assumed to have
no new capabilities. GET /presence lists every current member's device (`online`, `source` of `heartbeat`, `poll`
or `none`, intent, execution, blockers, agents, budget, schedule, capabilities, versions) and one entry per
person. Person identity comes only from verified links in the signed roster; names never merge identities. A person is `able`
when an online device reports intent `ready` (or an older lender is polling). Any current member can read it.

Hosts advertising `member_capabilities_v1` also accept a signed heartbeat body containing only
`capabilities`. This records member protocol support without changing lending presence, execution or
online status. Presence includes the last accepted `member_capabilities` and `last_capabilities_at`;
a later full heartbeat replaces that declaration. Current apps announce support in every approved
circle, including circles they only borrow from. Before publishing a changed roster `profile`, both
the owner and host require every other current member to have advertised `circle_profile_v1`.
The publishing device demonstrates its own support with the signed profile. Unknown support blocks
the change with `circle_members_need_update`; the local app names the computers that need updating.
Roster renewals and membership changes that keep an existing profile do not require a new declaration. Changes to signed person links or governance also require every other current member's
`circle_people_v1` declaration; authority-chain changes require `circle_authority_v1`.
The host checks support in the roster installation transaction, including members being
removed in that same update. Carrying unchanged governance fields through renewal does
not require a new declaration. Updated full heartbeats retain all these protocol capabilities.

The progress channel is optional and separate from the signed objects: it adds
endpoints and one schema (progress.schema.json) and changes no signed object. A
ProgressEntry is `{job, attempt, seq, at, step, kind}`. The lender sends only
`attempt`, `step` (1 to 120 characters, no control characters) and `kind`
(`step`, `done` or `fail`); the coordinator assigns `job`, `seq` (per job, from 1)
and `at`. Entries are not signed; the request proof authenticates the lender.
A lender SHOULD send at most one `step` every 15 s and 40 entries per run, and
MUST build steps only from the kind of action the agent took, never from file
contents, command lines or secret-file paths. A coordinator without the channel
answers 404 and a lender or reader MUST treat that as "no progress", not an error.
Entries are removed with the job's retention.

P8b also accepts `{attempt, stage, elapsed_s}`, stored as
`{job, attempt, seq, at, stage, elapsed_s}` on these same endpoints.
It is a separate variant: stage entries MUST NOT include `step` or `kind`.
`stage` is one of `preparing`, `agent`, `checks`, `screenshots`, `sending`.
`elapsed_s` is a nonnegative safe integer: whole seconds since this attempt
began preparing, measured by the lender's monotonic clock. It is reported
elapsed time, never a duration estimate or coordinator-verified evidence.
A runtime MUST emit checks or screenshots only when that phase actually runs.
Stage entries require an active attempt and share the 10 s minimum interval
and 40-entry per-attempt cap with action steps; only legacy done/fail entries
retain their interval exemption. All variants share the sequence and cursor.
Old lenders' step/done/fail bodies remain unchanged. Readers that do not
understand stages MUST ignore those entries while advancing the cursor.
An older coordinator can reject stage bodies with invalid_request; senders
MUST treat that as unsupported optional progress and keep execution working,
falling back to legacy action steps. No signed object or capability requirement
changes. Sender emission is a separate integration from coordinator support.

ClaimRequest contains advertisement and optional lease_seconds/wait_seconds.
Advertisement is device-scoped within that authenticated request: harnesses,
models, capabilities, egress, enforced_limits and max_limits. There is no
persistent presence/heartbeat registry in v1.0. Named claims and claim-next
use exactly the same matching rules. Claim-next additionally accepts optional
exclude: an array of at most 64 prefixed lowercase SHA-256 job digests. Invalid
entries or an oversized array are invalid_request. Exclusions apply on every
long-poll wake and are part of the signed/idempotent request body. They never
change a job's state or other lenders' eligibility. A lender SHOULD retain each
declined digest until the immutable job deadline, wait at least a few seconds
after any decline, and idle when 64 live exclusions are held rather than evict
one and reclaim it. Local off/pause, exhausted daily limits, missing ready sandbox
and an occupied approval queue MUST prevent claim-next before any job is claimed.
Renew body contains generation and optional
lease_seconds; release/fail contain generation and reason; stopped contains
generation and stopped_at. Server time, not stopped_at, governs authority.

JobView contains job_digest, full signed job, state, attempts_started,
current_attempt (null before first claim; most recent attempt thereafter),
and result_digest (null unless accepted). Result and attempt retrieval make
lost acknowledgements recoverable. Attempt lookup is durable for the retention
period; a client MUST NOT treat an unavailable response as an empty queue.

### Bounded transport, roster history and retention

The reference v1 HTTP transport limits concurrent requests to 256 globally and
64 per socket source address; forwarded address headers are not trusted.
After membership and the header signature are verified, held member work is
also limited to 16 requests per circle and 5 per member across body reads,
downloads. Bulk work has a separate ceiling of 192 host-wide,
48 per source and 4 per member. Heartbeat bodies use a separate allowance:
32 host-wide, 8 per source, 2 per circle and 1 per member. Thus one circle's
members cannot fill every slot, and short reads retain capacity even when
bulk work and heartbeat bodies are stalled. Smaller configured request/source
caps also reduce the held-work and circle ceilings; a single-slot configuration
necessarily cannot serve simultaneous requests.
JSON bodies are at most 262144 bytes and have a 15-second read timeout.
The proof's signed content_length MUST be a bounded nonnegative safe integer
before reading any bytes, including chunked JSON. An HTTP Content-Length,
when present, MUST agree. Actual streamed bytes MUST NOT exceed the signed
length, and the final digest/length MUST match. Ordinary member JSON requests
verify the header signature, freshness and current membership before buffering;
the nonce and authorization are checked again in the final write transaction.
Bootstrap enrollment and a new device installing its root-signed roster need
a public key from the bounded body; only those key-discovery cases defer the
signature check. Enrollment bodies instead use 2 slots per circle under a shared
host/source pool of 16, a 16384-byte maximum and a 2-second deadline. Nonmember roster recovery uses
its own pool of 2, a 65536-byte maximum and a 2-second deadline. Neither pool
holds a member request slot while waiting for a body.

Public invite resolution (`GET /v1/invites/{code}`) has separate valid-code and
unknown-guess budgets. Valid codes allow 30 lookups per code per 60 seconds;
unknown guesses allow 300 host-wide and per source per 60 seconds. Failed
unauthenticated requests have another 300-per-window host/source allowance.
Enrollment attempts and nonmember roster recovery share an independent work
allowance of 300 host-wide and per source per 60 seconds. Both are charged
before body slots or invite/roster cryptography; enrollment is also charged
before proof parsing. Exhaustion may deny new joins during an attack; it does not
consume authenticated member service or a valid invite's redemption allowance.
Successful enrollment admission allows 30 per verified device and 10 per
registered invite per 60 seconds, after the invite-key proof is checked.
Invalid proofs do not allocate durable nonce rows or successful-redemption
counters. Each rate map holds at most 4096 active keys; windows expire separately.
Nonce rows are capped at 100000 per circle and 2048 per device, and expired
rows are purged periodically in write transactions. Exhaustion returns 429
rate_limited without increasing the protected allocation.

Concurrent waiting claim/offer polls are limited to 4 per verified member,
16 per circle and 128 host-wide. Artifact downloads are limited to 2 per
verified member, 4 per circle and 16 host-wide. Parked polls release their general
request and body-work leases after acquiring the independent poll lease. Downloads
retain their request and held-member leases until completion, abort, deadline or shutdown.
A disconnected, timed-out, rejected or completed poll releases its slot.
Zero-wait claims do not hold poll slots. Claim candidates use indexed
state/deadline/requirements metadata; cheap eligibility checks precede signed
job verification. Poll wakes MUST NOT rewrite unchanged jobs.

The default per-circle quota is 10000 active plus retained terminal job rows.
Terminal job/attempt/result/cancellation bodies are retained for 30 days by
default (also the minimum configurable retention) and then collected in write
transactions. Compact, nonreusable job/result/cancellation identity tombstones and
original acknowledgements survive for the circle lifetime and do not consume
the live/retained-row quota. Exact authorized retries still return the original
acknowledgement, never create another execution; artifact blob collection is
separate and is not performed by this metadata-retention pass.

Clients fetch missing signing epochs from GET /rosters/{epoch} on demand,
verify the pinned root, circle, signature and exact epoch, and cache them as
history without lowering the current epoch/high-water mark. Historical
root signatures remain usable after roster expiry; archived records do not
confer present-day membership. A removed device cannot fetch any roster history.
On roster_stale or roster_unknown, a client refreshes the current roster once,
then retries with a fresh proof and the unchanged operation body/idempotency
key. A verified committed claim rejected locally is released when still live;
an expired or fenced replay is abandoned and the next claim uses a fresh key.
Network errors, 429 and 5xx preserve pending retries; a definitive completion
4xx records and surfaces rejection, clears pending publication, and permits
new claims.

### Submit and operation idempotency

Idempotency-Key is 1–128 ASCII characters from A–Z, a–z, 0–9, dot, underscore,
tilde and hyphen. The namespace is exactly (circle, authenticated device key ID,
key), shared by endpoints within that circle's database. Retries MUST retain
the original circle and absolute target. The stored identity
includes method, absolute target and **raw canonical body digest**.
Reusing a key with different identity is 409 idempotency_conflict, even when
the new body would otherwise be invalid for a different operation.
Auth/nonce checks occur first and are not bypassed by replay.

All JSON POST operations require the header. Records retain the original HTTP
status/body for at least 86400 seconds after successful/no-work outcome.
Concurrent identical submissions MUST join one committed outcome, not allocate
two jobs/attempts. A no-job 204 is retained too: a new poll uses a new key.
Heartbeat and no-job poll replies have separate bounded storage quotas from
user mutations. Both retain their full 86400-second replay window and share
the authenticated device/key namespace, so a key cannot switch endpoints.
The optional `control_idempotency_retention_seconds` capability reports this
window. Reaching either quota rejects new keys without evicting live replies.
Known not_applied errors need not be retained; a fresh proof with the same
body/key can retry after correcting the external condition.
Claim retry may return an already-expired original lease: client MUST GET the
attempt before resuming; response replay does not renew authority.

Publish additionally deduplicates the immutable Job digest for the lifetime
of the circle. An existing digest returns its original publish acknowledgement
even after the general idempotency window; it MUST NOT start another run.
Result completion additionally stores result payload digest, original
signed envelope and acknowledgement with the job. Exact canonical accepted
Result retries by the same current device return the original acknowledgement
even after lease expiry, terminal transition or the 24-hour key window.
A different Result is conflict; an old attempt on a different result is
stale_attempt. This lookup happens after authentication but before live-lease
checks. Revoked devices cannot use replay to bypass membership.

Cancellation similarly retains its first accepted digest/acknowledgement;
different reason/body after cancellation is conflict. GET Job/Attempt supplies
the latest cessation observation; replayed acknowledgements remain original.
PUT artifact is keyed by circle and digest, and MUST verify every upload
stream even if content already exists. Same bytes with different declared
media type/size is conflict. PUT roster uses root/epoch/bytes identity.

Terminal jobs, attempts, results and referenced artifacts MUST be retrievable
for at least 30 days after terminal transition (advertised retention may be
longer). Coordinators MUST retain nonreusable job/result/accepted-cancellation
identity tombstones and original acknowledgements for the circle's lifetime,
even after blob retention ends; expiry/GC MUST NOT allow a digest to be run
or accepted twice. Historical artifact availability is not perpetual.
Revocation overrides access even to retained acknowledgements.

### Pagination and long polling

GET /jobs: limit default 50, minimum 1, maximum 100. Return
`{"items":[...],"next_cursor":null|"..."}`. Cursor is opaque, authenticated
by the server and bound to circle, device, page size and a snapshot watermark.
Order is (published_at, job_digest) ascending; cursor uses keyset position.
Newly published jobs after the snapshot watermark appear in a new scan,
never duplicate/shift an in-progress scan. Item state is current at each page,
not a cross-page transactional snapshot. Cursors expire after 15 minutes;
malformed/expired/rebound cursors return 400 cursor_invalid, never silent reset.
An empty final page has next_cursor:null. Page length MUST NOT exceed limit.

**Job list negotiation.** On `/jobs` and `/offers`, a client names the job
features its validator can read in `Faravan-Client-Capabilities`, a
comma-separated list. This build sends `results_v1`, `parent_link_v1`, `source_manifest_v1`,
`working_directory_v1`, `filtered_git_v1` and `budget_v1`. The host omits jobs requiring
capabilities outside that list, except the original `patch-output` and
`verify_v1` capabilities. A `/jobs` request without `results_v1` also omits
typed results and `{kind:"none"}` sources. On `/offers`, an absent header
retains the cycle 1 `results_v1` view; the new source features still need
explicit tokens. Filtering happens before paging, so incompatible jobs cannot
end iteration early. `next_cursor` is null when the client's visible jobs end.
The parent capability is required for jobs with `parent`; both parent and source
capabilities and budget visibility are bound to the cursor view.
A cursor is bound to the view that issued it; presenting it with the other view
returns `cursor_invalid`. A legacy cursor issued before negotiation remains valid
for the legacy view. Signed jobs are never altered, and GET
/jobs/{job_digest} is unchanged. A coordinator that predates the header ignores
it and returns the unfiltered list.

claim-next waits at most wait_seconds (default 0, max 30) measured by server
monotonic time. It selects oldest eligible (published_at, digest) after
author/expiry/budget/requirements checks in the claiming transaction.
204 means no eligible claim was committed by that request. It does not mean
there are no jobs or all workers are healthy. On client disconnect no new
claim SHOULD be allocated, but a commit racing disconnect is possible:
reconcile the original idempotency key before opening another claim intent.
Long polling does not extend a request-proof timestamp or a lease.

On hosts serving several circles, a waiting poll releases its general request slot
after acquiring a separate host-wide poll slot. Enrollment bodies are bounded to two
per circle and sixteen per host by default; roster recovery has a separate capacity.
Broken stores are quarantined with exponential retry backoff up to thirty seconds.
An admitted invite miss retries at most one quarantined store before rechecking the
invite index. Misses remain retryable while unavailable stores may own their codes.
Router SQLite connections deliberately fail immediately on a competing writer so a
locked circle cannot pause every circle. A write may report a retryable failure or
an unknown outcome; clients reconcile and retry the original operation identity.

## 8. Requirements and capability negotiation

**Versions between the host and its members (P22).** GET /capabilities also reports `faravan` (the host's Faravan version, or null),
`min_member` (the oldest member version the host works with, or null; the host sets `FARAVAN_MIN_MEMBER`) and `capabilities[]`
(what this host can do: `heartbeat_v1`, `presence_v1`, `progress_v1`, `leave_v1`, `short_invite_v1`, `invite_revoke_v1`, `enrollment_reject_v1`, `network_requirements_v1`, `retention_v1`, `results_v1`, `offers_v1`, `circle_profile_v1`, `member_capabilities_v1`, `circle_people_v1`, `circle_authority_v1`, `parent_link_v1`, `frozen_audience_v1`, `source_manifest_v1`, `working_directory_v1`, `filtered_git_v1`, `budget_v1`, `model_effort_pairs_v1`, `auto_run_v1`). A host
built before P22 omits all three; a member reads that as `{faravan:null, min_member:null, capabilities:[]}`, and such a host is never
assumed to support a new field. A new field in a signed job, or a new route, is used only when the host lists its capability here and
(for work routed to a lender) the lender lists its own in its heartbeat. The client refuses to send a job with `requirements.network`
or `registries` to a host without `network_requirements_v1`, or a job with `result` to a host without `results_v1` (`host_too_old`, nothing is posted), and a lender posts progress only to a host
with `progress_v1`. A member older than `min_member` stops claiming and says which version it needs (status `update`); a host older
than the member's own minimum is the circle row of the blockers model. Members send `versions.faravan` in the heartbeat.

GET /capabilities reports protocol 1.0, circle/root/roster epoch, fixed lease,
page/wait/retry/idempotency bounds, advertised quotas/retention, supported
capability IDs/egress modes, max JSON/artifact bytes, archive limits and
input_protection:["none"], and artifact_head:true when HEAD is supported. A missing/false flag keeps the client's bounded GET existence probe; a capabilities 404/405 also permits that legacy fallback. HEAD returns Content-Length and Faravan-Media-Type with no bytes; subsequent result downloads still verify their full digest. Server capabilities describe admission vocabulary
and storage limits, **not proof of lender enforcement**.

Requirements use a closed vocabulary:
- harness: optional nonempty list of exact IDs, logical OR.
- model: optional {any_of:[exact IDs]}, logical OR; absence permits unknown.
- capabilities: mandatory array, logical AND; empty means no extra requirement.
- egress: provider-only or internet.
- limits: wall_seconds (1–86400); cpu (1–256 maximum concurrent logical CPU
  equivalents); memory_bytes and disk_bytes (1048576–1099511627776);
  output_bytes (1–1073741824, aggregate candidate plus transcript bytes).

All five numeric limit targets are mandatory fields. The optional closed
limit_modes object maps the same names to required or preferred. Each omitted
mode is required, including when the entire object is absent: existing signed
jobs retain their fail-closed enforcement requirements. Unknown names or modes
are rejected. A required limit must be enforceable at or below its requested
ceiling or the lender must decline; a preferred limit is best effort and never
by itself prevents matching. Unenforced preferred limits MUST be listed in
receipt.unenforced (disk_bytes maps to storage). limits_applied alone is not
evidence of enforcement; read it with enforced_limits and unenforced.
CLI/MCP defaults require cpu, memory_bytes, wall_seconds and output_bytes and
prefer disk_bytes. Old signed examples/vectors intentionally omit modes and
continue to require all five limits. See examples/requirements.preferred.json
for the default-mode example (an unsigned requirements block).

Wall time starts before preparing
the sandbox and ends after collection; upload may occur only while lease/job
authority remains valid and MUST NOT initiate new guest work. Memory/disk
include all job-controlled processes/writable storage; output enforcement
occurs during production, not only after an oversized artifact is created.
CPU is a rate/concurrency ceiling, not total CPU seconds. Lender policy may
apply stricter ceilings; Receipt MUST report actual ones and MUST NOT exceed
the signed request. Advertised max_limits describes the largest requested
ceilings a lender accepts. Lack of one required enforceable limit means
decline before claim. If capability is lost after claiming, stop and
release/fail rather than silently downgrade.

A claim advertisement MUST enumerate all enforceable limit names and egress
modes. Its enforced_limits array is a unique subset of the five limit names,
possibly empty; it need not contain all five. A job's required limits must be
present with sufficient max_limits, while missing preferred limits do not
prevent matching. The server matches requirements as admission metadata. The lender
independently verifies job signatures and probes its effective backend policy
before running. Advertisements/receipts remain signed-request/self-reported
claims, not attestation. Required model selection must be enforceable at
routing and reported consistently; it does not prove a provider's internal model.

provider-only permits only that job's locally selected model-provider service
through a narrowly scoped trusted proxy. It grants no general guest DNS,
package download, GitHub access or arbitrary provider-account API. A local
model endpoint is exposed through the proxy, never by allowing direct host/LAN
access. internet permits public internet but never host, LAN/private,
loopback, link-local, cloud-metadata, multicast, unspecified/reserved or
otherwise nonpublic destinations, for both IPv4 and IPv6. DNS rebinding,
redirects, tunnels, IPv4-mapped IPv6 and alternate encodings MUST NOT bypass
destination enforcement. Host/cloud-metadata ranges require defense beyond
just an RFC1918 list. Trusted input staging applies the same no-host/LAN/
metadata rule; it is not a guest egress exception.

Capability IDs MUST be locally recognized semantic contracts. The baseline
ID `patch-output` means the lender can return a text/x-diff candidate.
Unknown requirement keys, capability IDs, enum values, limit names, or
authority-granting semantics MUST fail closed. Jobs cannot set mounts,
privilege, host commands, network allowlists, provider credentials or arbitrary
backend configuration. Local installed adapter policy owns those choices.
A server or lender MUST NOT advertise enforcement that only exists as a
configuration field or untested inactive backend.

## 9. Artifacts and archive policy

PUT supplies exact Content-Length, Faravan-Media-Type and a proof binding
both. The media type of the upload body is application/octet-stream.
No multipart, chunked unknown-length or resume protocol in v1.0.
Stream to private temporary storage while hashing/counting; reserve declared
quota atomically before reading and abort at excess size/deadline. A deployment
MUST enforce per-device bytes/concurrent uploads and per-circle total bytes,
including pending reservations. Capabilities reports storage quotas; default
device quota is 10 GiB, circle quota 100 GiB, max artifact 1 GiB, and at most
2 concurrent uploads per device. Lower advertised quotas are allowed, including
max_artifact_bytes: 0, which permits only zero-byte artifacts.
Object counts are also charged transactionally: defaults are 10000 artifacts
per uploader and 100000 per circle, including each outstanding reservation.
Reservations temporarily consume a count even for duplicate digests; successful
duplicate completion retains only the existing artifact count. These private
configuration limits (`deviceArtifacts`, `circleArtifacts`) survive restart;
rejection is `quota_exceeded`, and no extra object or reservation is retained.
The byte counters in `/quotas` remain logical content-byte accounting.

Before allocating a new temporary file, the host checks filesystem headroom
with `statfs`, independently of logical quotas. Defaults retain 64 MiB of free
disk and 128 free inodes when the filesystem reports inode capacity. Reservations
across hosted circles charge the rounded content size (at least one reported
filesystem block), two metadata blocks and one inode until the transfer ends.
Filesystems without inode accounting still enforce byte headroom. Insufficient
headroom returns `rate_limited`; existing artifacts remain readable. This check
uses the filesystem's reported allocation unit, with no assumed 4-KiB block.
Other processes can consume space after the check; deployments that require a
hard physical isolation guarantee also need filesystem quotas or dedicated storage.
Release reservations on failure/disconnect/crash recovery; never buffer a whole
artifact in RAM. Final digest/length check and CAS visibility are atomic.
Repeated upload of the same circle blob does not consume additional retained
storage; temporary upload reservations still apply. Cross-circle dedup must
not create cross-circle read access or reveal existence before authorization.

The first successful uploader is charged retained bytes until that blob is
garbage-collected; the circle is charged once. Job publication and result
completion MUST atomically pin referenced same-circle blobs against GC for
their retention period. The reference store collects unreferenced uploads after
24 hours (`unreferencedArtifactGraceSeconds`), at most 128 per maintenance pass;
the client must publish before then or reupload. Deletion/retention is not a
license to reuse job identity. Terminal tombstones/acknowledgements are tiny
and retained independently.

Downloads require current membership on every request, stream bytes with
Content-Length, and use Content-Disposition: attachment plus
X-Content-Type-Options: nosniff. Clients verify signed expected digest, size
and context before use. Digests are identifiers, never access tokens.
No presigned cross-circle public download URLs in v1.0. A download's
authorization is checked at start; implementations SHOULD abort active
streams promptly after observed revocation, but cannot retract bytes delivered.

For application/gzip archives, consumers on both lender and borrower sides MUST:
1. Verify compressed size/hash first and extract only in a fresh disposable
   isolated directory, never over the caller's workspace.
2. Accept tar regular files/directories only. Reject symbolic/hard links,
   devices, FIFOs, sockets, sparse files and executable metadata hooks.
3. Reject absolute/drive/UNC paths, backslashes, NULs, empty components,
   dot/dot-dot components, duplicate paths, case/Unicode (NFC) collisions,
   and file/directory prefix conflicts. Reject result archives containing a
   `.git` path component at any depth (a hostile `.git/config` can run code
   when the borrower later uses git there); job sources from the borrower MAY
   carry one. PAX path/size and GNU long-name records ARE accepted (real
   repositories need paths over 100 bytes) and the resulting path is held to
   every rule in this list; other PAX keys that reinterpret types (sparse,
   SCHILY) are rejected.
4. Enforce at most 100000 entries, 10 GiB total expanded bytes, depth 64 and
   4096 UTF-8 bytes per path; the effective job disk/output limits may be
   smaller and take precedence. Reject more than 1 MiB of padding after the
   end marker. Enforce while decompressing where possible; the reference
   implementation (lib/archive.mjs) currently inflates with a hard output cap
   and checks limits before writing anything.
5. Strip ownership, setuid/setgid, ACLs/xattrs and timestamps; create directories
   privately and regular files nonexecutable by default. Preserve an executable
   bit only for job sources (the borrower's own files) or after explicit review. Refuse filesystem-following races.
6. Copy only validated regular content into another fresh review directory.
   Never auto-run hooks, project automation, binaries or candidate patches.
   Patch application is also untrusted and must reject path escapes.

This conservative portable tar subset intentionally rejects otherwise legitimate
archives; producers must package accordingly. Archive digest is compressed-byte
identity. There is no misleading duplicate tree_digest.

## 10. Cancellation and execution cessation

Cancellation revokes coordinator authority at transaction commit; its
acknowledgement sets authority_revoked:true. It reports compute_stopped only
from the existing holder cessation record, not from sending a signal.
requested_at is coordinator receipt time. The signed author created_at is
not a stop deadline or proof of cessation.

The lender observes cancellation through get/renew, revokes job-specific
provider access locally, stops the entire process/sandbox tree, performs
cleanup and reports stopped only after its trusted supervisor confirms no
job computation remains. The report is holder self-report, not a remote
attestation. Cleanup failures remain local operational work and MUST NOT
be represented as execution success. If no attempt ever existed,
compute_stopped:true is vacuously correct. Completed attempts do not
automatically imply cessation either.

Lease/job expiry and membership revocation also revoke authority without
confirming termination. An unreachable or revoked holder may be unable to
report through the member-only API; compute_stopped remains false/unknown.
No endpoint can undo already delivered provider requests or external writes.
Polling UI MUST distinguish requested, authority revoked and cessation
reported. A cancelled terminal job cannot later accept a result.

## 11. Versioning, extensions and v0 history

Path prefix v1, object schema names and signing domain are separate explicit
version commitments. Protocol 1.0 is frozen: unknown fields fail closed.
Future compatible functionality requires a negotiated, separately identified
schema/profile supported by both sides; an older v1.0 reader must reject it,
not silently drop signed fields. Incompatible meanings require v2.

The planned v1.x input-encryption seam is Job.input_protection. Its only
v1.0 value is none. Future negotiation may describe recipient-bound ciphertext
and key-delivery envelopes after claim, but this document deliberately does
not define algorithms, keys, rewrapping, confidentiality promises or an
enrollment-secret reuse mechanism. v1.0 rejects any other value. Claiming
device selection, job immutability and retry key delivery remain open design
work; a reserved seam does not mean encryption exists.

v0 is a separate historical reader, never implicit write fallback.
Retain the literal schemas `waspflow.faravan.task.v0` and
`waspflow.faravan.result.v0`, original JCS bytes/digests, Ed25519 domain
`faravan/<task|result>/v0\\0`, original key IDs/key material,
and mandatory-null oracle_ref/result_verdict/settlement. Existing optional
execution_metadata must be handled by its frozen historical validator.
Renaming the product MUST NOT rewrite old signed fields or domains.

The shipped preview at commit 78e592aa uses the literal `faravan/` domain
above. Earlier revisions of this specification named `waspflow-faravan/`;
that spelling does not verify this preview's evidence. The read-only
`lib/legacy-verify.mjs` preserves the shipped bytes and frozen validator,
with no signing, transport or execution API. Evidence from another historical
domain requires its matching pinned implementation; no fallback is attempted.

Historical verification MAY ignore task expiry solely to verify old evidence,
and MUST label expired/revoked/legacy status; it MUST NOT grant current
execution authority. Preserve known historical v0 keys independently of the
coordinator's latest roster. v0 key IDs are not assumed to be v1 fingerprints.
An old valid signature does not prove the v1 author/holder equalities or
independent root authorization were enforced. v0 SETTLED means recorded result,
not evaluation/payment. Old public digest routes and shared bearer access
are not part of v1. Safe migration publishes a new explicitly signed v1 job
with a new intent, never mutates/re-signs a historical object in place or
automatically re-executes it.

## 12. Security and implementation gates

An implementation MUST test independent identity binding, anti-rollback and
revocation, atomic concurrent claims/completions/cancellation, stale-generation
rejection, lost-ack retry, claim-time expiry, enforced resource/egress policy,
streaming quotas, malicious archives and authorized downloads. Passing JSON
Schema or an old hermetic unit suite does not establish these runtime claims.

Which accounts and backends a lender offers is the lender's choice. This
protocol adds no provider-terms or account-eligibility gate and makes no claim
about them.

Keep provider credentials on the lender host behind narrowly scoped,
budgeted, revocable access; a guest that can call a proxy still has costly
authority. Avoid host-network access and hidden environment secrets.
Signatures authenticate provenance rather than correctness/model use.
Render transcripts as inert text and scrub secrets before upload; truncation
must obey output budgets. Owner root backup/compromise response is operational
security, not a coordinator feature.

This proposal addresses the audited gaps without claiming source fixes:
architecture F1/F4/F10 -> transactions, bounded attempts and explicit outcomes;
F2/F5/F6 -> portable requirements and truthful enforcement declarations;
F3/F8 -> root-pinned identity, mandatory consumer verification and artifact
safety; F7/F12 -> versioned wire definitions and frozen v0 history;
F9/F11 -> headless native state and independent conformance gates.
The security audit's roster substitution, identity mismatch, public digest
access, unbounded uploads, unsafe extraction, receipt overclaim and
cancellation/concurrency concerns motivate the normative requirements here.

Prior art by name only: SQS visibility timeout informs renewable visibility
with duplicate execution; Temporal informs durable operation/attempt
reconciliation; GitHub Actions JIT runners and Buildkite agent inform
outbound pull and short-lived execution authority; BOINC informs separating
returned work from independent validation; A2A 1.0 and MCP Tasks inform
thin requester adapters, not core lease semantics.

## 14. Open questions

1. Enrollment is necessarily a bootstrap exception to literal “every write is
   a current member”: the pending request proves the new device and root-signed
   invite but grants no operational access. Resolved by section 14.1's
   one-time invite-key approval.
2. Root-only membership authenticity cannot stop a malicious coordinator from
   equivocation or hiding revocation until roster expiry. The default is seven-day signed
   rosters with a thirty-day maximum; is an
   independently reachable freshness/transparency service needed?
3. Root rotation/recovery, owner emergency cancellation after author-device
   loss, and stronger multi-device human identity need separate approved
   protocols. v1.0 uses author key identity; revoking that key cancels its
   active jobs on an honest coordinator.
4. Confirm the operational defaults: 30/120/300-second leases, three attempts,
   1-GiB blobs, 10/100-GiB quotas, 30-day retrieval and lifetime identity
   tombstones. Lease/result uniqueness is scoped to one honest coordinator.
5. v1.x encryption must reconcile immutable jobs, post-claim recipient
   selection, retries and revoked recipients. No cipher/key-delivery design
   or confidentiality guarantee is implied by input_protection:none.
6. (Removed: provider terms are the lender's choice, not a protocol question.)
7. Test-only cryptographic vectors accompany this pure library. Endpoint/race
   tests and runtime policy conformance remain required before declaring any
   server or execution implementation v1.

### 14.1 Owner decisions on the open questions (2026-10-09)

These amend the text above. Where they conflict, this section wins until the
body is revised.

- **Q1, enrollment: approve by invite key, not by a human comparing
  fingerprints.** Comparing fingerprints over a side channel is too much to ask
  a non-technical lender. Instead, each invite carries a one-time **invite
  signing key**. The owner's device registers only the invite's public key with
  the coordinator; the private key is carried inside the invite link
  fragment and must be handled by trusted code as described in section 5.1.
  The joining device signs its device public key with the invite
  private key. The owner's device (not the coordinator) verifies that signature
  and then publishes the next root-signed roster automatically, with no click.
  A coordinator that has not captured the fragment sees only the public key,
  so it cannot enroll a substitute device. An owner MAY switch a circle to
  "approve each device" mode, in which the owner's app shows the request and
  one button. If the owner's device is offline, the enrollment stays pending
  until it returns.
- **Q2, roster validity: default 7 days, maximum 30 days, refreshed
  automatically.** A 24-hour limit would stop a whole circle whenever the
  owner's laptop is closed for a weekend. The owner's device re-signs the
  current roster whenever it is online and the roster is more than half way to
  expiry. Revocation takes effect at once on an honest coordinator; the bounded
  stale-view window against a malicious coordinator is the roster validity,
  which the owner can shorten per circle.
- **Q3:** accepted as out of scope for v1.0.
- **Q4:** accept the defaults as proposed for v1.0; revisit with field data.
- **Q5:** accepted as v1.x work.
- **Q6:** out of scope for the protocol. Which model access a lender uses,
  and its terms, is the lender's choice; the product is unopinionated about
  backends.
- **Q7:** required before any implementation advertises v1; tracked as an
  implementation task.

#### Additional owner-approved wire details (2026-10-09)

All signature domains use the renamed `faravan/` prefix, including enrollment.
Receipts remain unsigned and embedded in Result; their vector is JCS + digest,
not a new receipt signature domain. Enrollment/link bytes are specified in
section 5; domain/circle/invite/device binding prevents cross-context reuse.
The full RFC8785 encoder is distinct from the integer-only wire profile in 3.1.
These clarifications are also part of section 14.1's owner decisions.

The pure library does not implement HTTP, nonce storage, durable anti-rollback,
one-time invite consumption, membership publication, or execution policy.
Request verification requires independently expected metadata, including signer
fingerprint, circle and roster epoch. Callers verify current roster membership
first, inject integer Unix-seconds clocks, and supply an atomic consumeNonce
callback returning true only once within the proof-validity window. Both proof
helpers pass (key_id, nonce, expires), where expires is the conservative
receipt-time + 361 seconds retention bound. A callback may use that bound as
supplied, or derive the exact earliest deletion time from the verified signed
created value: created + 301 seconds (section 3.3). It MUST retain the tuple
through the inclusive created + 300 boundary. The domain store uses this exact
created + 301 expiry; a callback without the verified created value must use
the supplied conservative bound. Raw upload metadata may be stream-computed
outside this library; it never buffers an artifact stream.
Same-epoch roster checks require the remembered payload digest as well as epoch.
Signature verification alone never returns an authorization verdict.

## 15. Verification scope

The JSON schemas express field/type/closed-vocabulary constraints, not all
semantic, cryptographic or concurrency invariants. The JSON example files and golden vectors use explicitly synthetic test keys.
Signed inline lifecycle examples match the same test-key envelopes; artifact
references and server acknowledgements remain illustrative rather than a running server. OpenAPI 3.1 describes the API and its
request-proof header, with cross-field/state requirements normative here.
See the assignment report for the actual checks executed and their receipts;
this design document does not predetermine a passing result.

### 15.1 Synchronous domain-store boundary

The library in lib/v1/store.mjs is one pinned circle per SQLite database, not
an HTTP server. Provisioning a fresh database requires circle, origin,
rootFingerprint and an initialRoster from a trusted out-of-band source.
Reopening may supply only path and clock; supplied pins must match.
The optional idGenerator is for tests; generated identifiers must be canonical
UUIDs. All public operational methods require a fresh signed RequestProof,
verify it via lib/protocol, and check current membership inside BEGIN IMMEDIATE.
Roster replacement uses the proposed-roster authentication exception in section 5.
The optional quotas configuration can lower the default admission limits.

Domain methods throw ProtocolError with section 7 stable codes. The synchronous
proof helper consumes a nonce in the same transaction. A savepoint isolates
domain changes: authenticated unsuccessful operations retain their consumed
nonce, while rolling back their domain mutations and idempotency record.
Successful POST outcomes, including no-work null, retain their returned value
under device/key plus method, absolute target and canonical-body digest.
The transport layer in lib/v1/server.mjs maps these values to HTTP status/body. Signed Job.max_attempts remains mandatory in the frozen schema:
job-building callers use 3 as the default, rather than altering signed bytes.

Artifact methods accept metadata only. reserveArtifact verifies the original
PUT proof and charges pending quota. The trusted caller must stream/hash/count
bytes separately and pass its observed metadata to commitArtifact; metadata
commit does not itself prove that a blob was stored. Invalid completion metadata
releases the reservation without publishing it. Disconnect handling releases
the reservation explicitly. On restart, listArtifactReservations and
recoverArtifactReservations let the authenticated uploader reconcile and
release its own durable reservations after its upload workers have stopped.
Opening another connection MUST NOT release another live connection's
reservations. There is no automatic timeout-based reservation recovery.
Unreferenced metadata is collected after its grace period; current reservations
protect their digest, and pinned job/result references retain their files until
the owning jobs are retired. The HTTP owner removes collected files only after
commit and rechecks ownership before retrying a failed removal. Blob durability, streaming,
temporary-file recovery and byte-store atomic visibility remain transport/storage
integration obligations.

The signed /artifact-reservations targets remain internal metadata operation identities, not public HTTP endpoints. Section 7 now specifies authenticated /invites and /quotas routes. Public adapters must preserve atomic
proof, reservation and metadata authority while mapping their wire operations;
they must not expose a client-controlled assertion that upload bytes were verified.
Enrollment rejection is a current-device maintenance action and grants no
membership; approval still requires the root-signed roster.

Every request handled by run(), including a GET or HEAD, performs maintenance
inside the same BEGIN IMMEDIATE transaction before authentication and the
domain savepoint. Maintenance removes expired nonce, idempotency, cursor and
bootstrap-rate records; it can persist expired Job/Attempt state and collect
terminal job bodies after the configured retention period, preserving durable
identity tombstones. Successful reads therefore may commit these changes as
well as fresh nonces and opaque durable cursor tokens. Authenticated domain
failures roll back to the savepoint but retain maintenance and nonce changes;
authentication failures roll back the transaction.

Read-view normalization itself remains a projection, separate from maintenance;
it does not independently save every projected lease or membership transition.
Cursor membership, limit, expiry, keyset position and insertion-sequence
watermark are stored server-side; same-second later inserts are excluded from
an existing scan. All persisted maintenance and domain transitions use the
same serialized transaction rules.

Closing a connection between transitions and reopening tests committed-state
recovery, not a process kill during a SQLite commit or storage power failure.
Worker-thread barrier tests use simultaneously live separate SQLite connections;
they demonstrate serialization on one local database, not distributed consensus.

### 15.2 HTTP adapter and local provisioning

v1.0 runs one circle per queue server. Trust is provisioned LOCALLY, never by
a first network caller. A public provisioning JSON file has exactly
{circle_id, origin, root_fingerprint, roster}, with a root-signed epoch-1 roster.
Run faravan-coordinator --v1-provision FILE on the coordinator host. The
exported provisionV1Store({path,provisioning,clock}) verifies the pinned root,
circle, roster and origin, initializes a new database, and closes it. Existing
database paths are refused; this command cannot replace a trust pin.

The process requires FARAVAN_COORDINATOR_V1_ORIGIN, with database <coordinator-home>/v1/coordinator.sqlite
and blobs <coordinator-home>/v1/blobs. Programmatic startCoordinator accepts
v1:{dbPath,blobDir,origin}; v0 options, routes and authentication are retired.
Before provisioning, v1 requests return 404 circle_not_provisioned. An unknown
circle at a provisioned server receives the same code. The server picks up
local provisioning on the next v1 request; no network root replacement exists.
The configured external origin must be normalized HTTPS, literal-loopback HTTP, or signed explicit LAN HTTP as defined in section 7;
Host and forwarded headers never choose a proof target. TLS is terminated by the
operator's reverse proxy.

createV1Handler({store,blobDir,clock,limits}) exposes close() and a pendingPolls
count. The optional limits can tighten maxBodyBytes, maxArtifactBytes and
maxPollSeconds; uploadTimeoutMs bounds incomplete streams. Control bytes are
bounded before buffering. Artifact PUT authenticates and reserves first, hashes
and counts into a private temporary file without buffering the artifact, fsyncs,
then atomically renames to the digest path within the synchronous metadata
commit. A crash between rename and database commit can leave an inaccessible
orphan CAS file; no metadata is published until the transaction commits.
Commit failures return unknown outcome and clients reconcile the original digest.

The HTTP adapter owns an exclusive process lock beside its blob directory.
Concurrent live owners are refused. An existing lock always fails closed, including after an unclean exit; there is no automatic stale-lock takeover. An operator must first verify that all prior coordinator processes have stopped, remove the stale <blobDir>.http-owner lock offline, and restart. Only after exclusive ownership is acquired does startup remove transport-owned reservations and .upload temporary files; direct domain-store reservations remain under explicit authenticated recovery. Lock release verifies the owner's unique token. Blob and SQLite paths must stay paired and be private to this
single coordinator. Process-kill/power-loss recovery is not claimed by the
loopback integration tests.

Long-poll continuations authenticate once and consume one nonce, then recheck
membership, exact epoch and proof age in each claiming transaction. Concurrent
identical polls join the same retained result. A final no-work 204 is retained;
disconnect cancels listeners/timers without allocating a later claim. Publication,
release, failure, cancellation and roster changes wake polls. No background
lease sweep or distributed notification bus is implied.

Enrollment pages default to state=pending, limit=50 (1–100), with 15-minute
opaque device/filter/limit-bound snapshot cursors and ordering by created_at,
enrollment_id. Owner approval still verifies each returned enrollment_proof
against the independently registered invite key before signing a new roster.
